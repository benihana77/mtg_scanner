I am still not totally happy with how tokens are handled. There are a couple of issues. 1) What is the intended behavior when new tokens are added? Right now, the "set" for a token is still the natural set, but the "Section" is TOKEN. however, when a new chunk includes tokens, how would this be annotated? Would the "Section" need to become TOKEN-1 to indicate that it is a new chunk of tokens? Or would I need to interleave the new tokens alphabetically into the TOKEN section. 2) There is no good, standard way to define token sets. In modern sets, tokens are a "subset" of the main set, eg TMOM denotes the March of the Machiene Tokens. But this has not always been true. For instance, the card https://api.scryfall.com/cards/545639fc-e521-41f2-81b2-a671007321eb?format=json&pretty=true is a Demon Token that was included in a Dual Deck (DDR). This should be considered a token, and not part of the DDR set, and should be sorted with the tokens. But how would the tool know to sort it this way? Furthermore, if someone were to order that card, how would the tool find it in the right place, and deduct it from inventory? 

It seems to me like there are two options 1) Keep the current setup, get smarter about how token sets and sets that contain tokens are handled. Keep the set of the card the same (the natural set code) and update the section to become TOKEN-1, TOKEN-2, etc to denote the new chunks of tokens as the are added 2) Mix the tokens back into the sets that they belong with. Each "Set" would include a "TOKENS" section (eg MOM would have Section-1, Section-2, and TOKENS) At the time of putting away cards after listing, I would have to manually pull out the tokens and put them into the correct physical section. This would be weird since it would lead to a divergance between the SQL and the physical inventory, which is an idea I dont love.

Help me plan solutions to this edge case. Do not make any changes yet, I want to brainstorm this out before we change anything.

For additional reference, picklist-2026-10-08.csv contains an example of how a token would show up in the ManaPool picklist. 

After doing some research, I think the "layout" field in the scyfall api might be the best bet for determining tokens/emblems. It seems to be the only field that is constant between the edge cases that I can think of (like the dual decks, older sets, etc). I think we would want to include layout==emblem in these cards as well, since they are usually part of the "token" sets, and that is normally how I think of them
